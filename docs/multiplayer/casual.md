# Casual control and absence

The server transfers a disconnected human seat to temporary bot control immediately. Each original owner has 180,000 milliseconds of cumulative absence per match; a return strictly before the deadline consumes elapsed absence and leaves the remaining budget for later drops. Multiple missing owners have independent clocks. Intentional Leave immediately transfers permanent bot control. Deadline processing clears an expired seat's deadline and makes its bot control permanent. Accepted moves and terminal results remain final.

`domain/casual.ts` contains candidate-only transitions. `CasualService` authenticates the original owner's private credential, reloads/rechecks the current connection identity on up to 16 CAS retries, persists the candidate revision, and then publishes. The invite code cannot reclaim a seat. These helpers change connectivity/control only; they never change an army's alive state or board. Terminal returning owners receive the result through the HTTP recovery endpoint without reopening play.

`freezeAbsence(record, cutoff)` settles only time before the last durable service observation and stops the absence ledger. `returnedOwner` keeps the settled budget when the owner returns during recovery. At the end of recovery grace, missing owners resume absence at the current time with the saved remaining budget; outage time is excluded. Departures already expired before the service cutoff remain permanent.

Empty casual bot seats receive stable internal owner identities from `initializeBotOwners` at match start. They have no client credential and their identities are excluded by the public snapshot allowlist. Temporary/permanent replacement bots use the original seat's private identity solely through the trusted server adapter.

`BotScheduler` selects from the canonical generated engine's `chooseAiMove`, with injected clock, random source, node budget and scheduler. Its default medium policy uses at most 128 nodes. One job is guarded by match ID, revision, current color, owner, controller and scheduler generation. It cancels on lifecycle changes/disposal, excludes ranked and frozen armies, and routes selected moves through the shared `CommandProcessor`. The processor revalidates phase, ownership, turn, deadline and revision and persists before publishing. Reclaim and bot moves compete for the same durable revision; accepted bot moves are never rolled back.

The Room adapter checks absolute deadlines before authentication and every incoming command, on scheduled maintenance, and after bot work. It persists overdue departures before scheduling from the latest accepted snapshot. Production recovery hooks also expire the service recovery grace before command/reclaim admission. Storage rejection leaves the durable board unchanged. Shutdown cancels bot work and suppresses player Leave consequences.

Tests exercise boundary timing, repeated/simultaneous drops, concurrent reclaim, stale session callbacks, lifecycle cancellation, frozen armies, and revision guards. The real SDK integration starts the canonical 36-piece position with two humans and two bots, drops and reclaims a human after an accepted replacement move, then finishes while that owner is absent and returns the final result through HTTP. Human moves in this bounded seeded test are selected by the canonical AI and sent through the SDK; bot moves use the server scheduler and shared processor. This verifies the transport/lifecycle in the memory adapter, not live PostgreSQL durability.
