# Ranked account identity

The server adapter uses the approved `@supabase/supabase-js@2.117.2`. Supply `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` through server configuration. Only an HTTPS project root and a public publishable key (or legacy public anon key) are accepted; service-role keys are rejected. Neither values nor tokens are logged by the adapter. Missing configuration leaves identity unavailable; ranked enabling and durable admission locks belong to server composition.

`createSupabaseIdentity(config)` returns the invitation route's `verifyAuth(authorization)` function. Missing authorization returns `undefined` for casual guests. Every supplied malformed, oversized, expired, anonymous, revoked, unavailable or otherwise invalid identity rejects with only `unauthorized`. Account IDs come exclusively from verified Supabase UUIDs, bound to the configured project's exact `/auth/v1` issuer. Client bodies, platform usernames and stored browser session objects never establish server identity.

The official SDK's `getClaims(token)` verifies the JWT signature with WebCrypto and the project's JWKS, falling back to Auth-server verification when required. The adapter explicitly checks issuer, authenticated audience and role, UUID subject, issued-at, expiry and optional not-before against its clock. It then always performs a fresh `getUser(token)` request, requiring the same non-anonymous account and rejecting active or malformed ban deadlines. It never authorizes with `getSession()`. Session persistence, automatic refresh and URL session detection are disabled. Provider fetches allow only the configured Auth user/JWKS routes, reject redirects, cap response bodies at 64 KiB and have a whole-verification deadline (default five seconds, maximum ten). Provider failures are fail-closed and expose no provider diagnostics.

Local tests generate EC/RSA signing keys and real JWT signatures, with simulated JWKS and Auth responses. They require no live project, accounts, email delivery or database. Passing them proves adapter behavior, not live provider or deployment acceptance.

The supplied project currently has email authentication enabled; social providers have not been enabled. Client sign-in, social-provider configuration and external-frame sign-in with a manual return-code fallback are later client work. Platform accounts are not automatically linked to Supabase identities. Live email, account creation, provider changes and deployment remain separately authorized actions.

API references: [Supabase getClaims implementation](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueClient.ts) and [official client custom-fetch configuration](https://github.com/supabase/supabase-js/blob/master/packages/core/supabase-js/README.md).
