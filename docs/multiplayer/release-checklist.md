# Client packaging and release gates

The canonical editable sources are `index.html`, `chaturaji.html` and `enochian.html`. Packaging never changes them. Run `node scripts/package-client.mjs` to generate the default `dist/chess-eternal-blitz.zip`. Its only entries are those three exact-case HTML filenames at the ZIP root. Serve the extracted directory over same-origin HTTP, including from a subdirectory; opening the launcher alone does not prove offline or platform compatibility.

Run `node scripts/package-client.mjs --single-html` to generate the same ZIP plus optional `dist/index.html`. This generated page embeds literal JSON source strings, escaping HTML delimiters and Unicode line separators. It changes only the generated launcher loading boundary to use `srcdoc`; both frames load lazily once and retain their browsing contexts. No separately maintained game copies or whole-game Base64 payloads are used. Existing inline art, pinned SDK/license, protocol and engine metadata, storage keys and direct parent statistics bridges survive through exact decoded source parity. The optional export needs no game-page fetch or runtime CDN; multiplayer still requires an approved HTTPS/WSS backend. A single client HTML file does not include a backend.

Both exports contain client pages only. No server source, migrations, private tests, environment files or database credentials are added. Configure only the public HTTPS/WSS endpoint through the supported client setup. `dist/` is already ignored. ZIP entries use STORE compression, fixed entry order and a fixed 1980-01-01 timestamp, with no extra fields/comments; identical source bytes produce identical artifacts independent of compressor versions and local time zones. Optional HTML preserves canonical source line endings outside its generated loader. Do not edit generated output.

## Local executable checks

- `node --test tests/client-packaging.test.mjs`: exact ZIP content and CRC/directory integrity, deterministic bytes, hostile closing-script serialization, canonical decoded game-byte parity, unchanged launcher outside the loading boundary, parent bridge preservation, lazy one-time assignments/state retention and retry behavior.
- `node scripts/check-client-preservation.mjs`: canonical Chaturaji and launcher preservation plus the approved Enochian boundaries.
- `node --test tests/*.test.mjs` and the approved backend suites: run against disposable/local resources before release; record results separately from actual platform/device acceptance.
- Rebuild after any canonical page change. Compare artifact hashes and unpack with an independent ZIP reader before selecting the upload file.

The packaging unit tests exercise the generated loader in a DOM harness. Root also verified actual browser loading from `/package/index.html` over same-origin HTTP and Enochian inside the generated `/standalone/index.html` `srcdoc` frame. After starting a CPU turn, returning to the outer menu beyond its delay and reopening the standalone game retained the initial board: hidden CPU work did not advance it. Fixture request counts showed the standalone page made no game-page requests, while the three-page package fetched its relative Enochian page. These checks do not establish platform compatibility or separate physical-device acceptance. The remaining release gates stay **UNVERIFIED** until separately exercised.

## Required release acceptance

- Same-origin HTTP subdirectory preview of both packaging forms: both menu paths, retained game state, shared-statistics result recording, inline artwork, mobile layout, fullscreen and audio. Confirm no game-page requests for the optional export and no CDN dependency for either form. Repeat hidden/reopened CPU-session lifecycle checks against the actual generated `srcdoc` frame.
- Authorized itch.io and Newgrounds draft uploads: ZIP root paths, nested frame behavior and actual request Origin values from relative `src` and optional `srcdoc` frames. Observe actual origins before configuring the exact server allowlist; do not infer them from the outer platform page. Null origins remain denied until a secure alternative is explicitly approved. Draft upload and publication are separate authorized actions.
- HTTPS/WSS staging: authentication, manual room-code fallback, recovery, reconnect and Railway transport/restart acceptance. Check raw HTTP matchmaking/preflight payload and rate coverage, proxy trust and one-process deployment/drain behavior described in [operations](operations.md).
- Casual matches on **2–4 separate physical devices**, including bots, reclaim/expiry, captured kings and approved atomic exchange. Browser tabs do not satisfy this requirement.
- Four-human ranked staging match on separate devices: account admission, pause/resume, timeout/penalty, final settlement and durable restart/recovery. Ranked remains disabled until product gates, account configuration/live providers and these acceptance checks pass.
- Railway creation and deployment are approved: the project/service/domain exist, one US East replica and no sleeping are configured, and the workspace compute cap/alert are saved. Deployment and external acceptance are recorded separately in operations. Platform draft uploads and publication still require explicit authorization.
- End-only independent specification and quality reviews, followed by final user release review. Passing local tests does not authorize publication.

Operational rollback uses the previously verified client artifact together with its compatible backend protocol/engine version. Retain the exact release artifact and hashes privately with the release record; do not mix a new client with an incompatible server. Follow the database backup, recovery and controlled-deployment procedures in [operations](operations.md); packaging performs no database work.
